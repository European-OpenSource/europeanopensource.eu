10. Project Submission & Admission Criteria

10.0 Public information & origin of listings

Projects listed in the Catalog are submitted publicly via GitHub Issues, either directly by opening an issue on our repository or through the submission form on this website (which creates a GitHub Issue asynchronously). The entire review process is transparent and takes place on GitHub, where anyone can follow the discussion. Information displayed is sourced from public materials (repositories, registries, official project pages) and is presented without alteration by European OpenSource. We are not responsible for project code or security; we perform basic checks only to confirm our criteria and eligibility for open-source listing. Project data may change over time and is not guaranteed to be up-to-date in real time. Please report errors, abuses or non-compliance tosupport [@] europeanopensource [.] eu

10.1 Mandatory Eligibility

Projects must satisfy ALL mandatory criteria:

  • Geographic eligibility: At least one of: (i) legal entity incorporated in a country within the European Union (EU), the European Economic Area (EEA), the United Kingdom (UK) or Switzerland (CH); (ii) majority of founders or beneficial maintainers hold citizenship in the EU/EEA/UK/CH; (iii) primary maintainer holds citizenship or residency in the EU/EEA/UK/CH.
  • Values alignment: Tangible commitment to privacy, accessibility & inclusivity, sustainability / responsible digital practices, and contribution to public good.
10.2 Quality (Accelerated Review)
  • Clear problem–solution fit & measurable impact.
  • End‑user documentation & usage guidelines.
  • Developer / contributor documentation.
  • Identifiable, contactable maintainers.
  • Active maintenance cadence (recent commits / releases).
10.3 Submission Process
  1. Submission via GitHub Issue: Open a GitHub Issue on our public repository using the project submission template, or use the submission form on this website which creates the issue asynchronously (note: form submissions may take some time to appear as a GitHub Issue).
  2. Public Review: Maintainers evaluate the submission publicly on GitHub. Once the project meets the eligibility and quality criteria, a maintainer applies theapproved-submission label to the issue.
  3. Automated Validation: Applying the label triggers an automated workflow that validates the submitted project data against the catalog schema. If validation fails, a comment is posted on the issue detailing the errors no pull request is created until the issues are resolved and the label is re-applied. If validation passes, a pull request is opened automatically.
  4. Publication: Once the pull request is reviewed and merged by a maintainer, the project is added to the catalog and published on the platform. Visibility may include feeds, newsletters or social dissemination.
10.4 Removal & Discretion
  • Ongoing compliance: Projects may be de‑listed if criteria cease to be met or if new criteria apply retroactively.
  • Editorial discretion: We may reject or remove Projects for broader reasons (e.g. legal risk, ethical concerns, quality assurance, brand/reputation protection).
  • No guarantee: Compliance does not ensure publication; decisions are at our sole discretion.
  • Communication: All communication regarding the submission status takes place publicly on the GitHub Issue. Submitters should follow the issue for updates.
10.5 Criteria Evolution
  • Adaptive: Criteria evolve with European digital sovereignty priorities & best practices.
  • Retroactivity: New criteria may apply to existing listings; affected Projects will be given a reasonable adaptation period before removal.
  • Notice: Material changes communicated where reasonably feasible.
